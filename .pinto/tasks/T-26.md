## why
`create_hold` validates the book token, then does its side effects, then consumes it. Two requests carrying the same token both pass validation before either consumes, so a double submit or a platform retry can book twice. This is not theoretical: during the T-19 live proof one invocation booked `hld_ec510ff1` while its sibling asked calrs for the slot its twin had just taken and returned `slot_unavailable`, so the caller saw a failure for a hold that exists.

## scope_in
- Atomic claim of the book token before any side effect, so exactly one concurrent request proceeds.
- Release the claim on every refusal after the claim, keeping the T-19 guarantee that a refused hold leaves the token usable.
- Store methods for claim/release in both the Turso and memory implementations.

## scope_out
- Idempotency keys or a request-dedupe cache.
- Changing any named error, HTTP status, or the create_hold control flow beyond the claim.
- calrs-side deduplication.

## acceptance_criteria
- [x] A second `claim_token` for the same token returns false while the first claim holds, in both the memory and Turso stores. Claiming a token that does not exist returns false.
- [x] `create_hold` claims the token before the calendar action. Losing the claim returns `token_invalid` and touches nothing: no calendar booking, no Nathan hold mail, no `booking.requested`, no hold row.
- [x] Every refusal after the claim releases it, so the book token still works afterwards: `slot_unavailable`, `hold_cap`, and mail-fail-after-create all leave the token usable. The T-19 criteria that assert this stay green.
- [x] A successful hold leaves the token consumed; replaying it returns `token_invalid` `already used`.
- [x] `npm run test:interview` green, including a test that claims twice and asserts the second attempt loses.

## notes
- 2026-08-28: the claim is a conditional update, so it is atomic rather than a read-then-write. Turso uses `UPDATE ... WHERE token = ? AND consumed = 0 RETURNING token` and treats an empty result as a lost claim; the memory store mirrors it. `create_hold` claims before the cap check and every later refusal calls `release_token`, so slot_unavailable, hold_cap, missing magic secret, and mail-fail-after-create all still leave the token usable. The success path no longer calls `consume_token` — the claim already consumed it.
