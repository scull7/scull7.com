## why
Recruiter agents need a real way to interview Nathan Sculli against published facts and, after the recruiter verifies a work email, request a tentative calendar hold. The static resume site is not that product.

## scope_in
- Implement interview-me v1 per [`docs/INTERVIEW-ME.md`](../../docs/INTERVIEW-ME.md): named sessions and a booking request.
- First user: recruiter agents interviewing Nathan Sculli (not Nathan practicing).
- Cited Q&A from `resume.json` and public site pages; refuse anything not in that corpus. No invented career facts.
- Work-email verification (magic link, human click, short-lived book token scoped to that session) before any calendar hold. Q&A stays open without verification. The agent never needs inbox access.
- A booking request creates a tentative calendar hold on the configured booking backend (calrs). The event type owns the meeting length; the stored hold defaults to 1 hour. Which backend/event type is used must be configurable.
- Persist sessions, tokens, and holds in Turso (not Netlify Blobs).
- Free-email blocklist defaults: gmail, yahoo, hotmail, outlook.com, icloud. The list must be configurable. Creating a hold emails Nathan a notification with one-click **ban this address** and **ban this domain** links.
- A work domain may have at most N active tentative holds at once. Default N=3. The cap must be configurable.
- Booking / `create_hold` is allowed only after the session has completed the required question set. Refuses do not count as completion. Default set (five items, must be configurable, same rule as the blocklist): cited answer on current work (TensorWave / Relay); cited answer on leadership scale; cited answer on systems depth (Rust / distributed systems); cited answer on what Nathan wants next; hiring timeline stated by the recruiter (their fact, not a resume citation).
- Real OpenAPI at `/openapi.json`, MCP at `/mcp` (tools: `start_interview`, `ask_nathan`, `request_verification`, `create_hold`, `get_resume`), and optional `callback_url` webhooks (`interview.completed`, `booking.requested`).
- Update `llms.txt` when-to-use for this product.

## acceptance_criteria
- [x] Recruiter agents can start a named session (company, role, recruiter name, work email) and ask questions that return cited answers from the published corpus, or a refusal when the fact is not published.
- [x] Q&A works without verification. A calendar hold is impossible until the work email is verified.
- [x] Verification is a human magic-link click; the agent receives a short-lived book token scoped to that session and never needs inbox access.
- [x] Create hold (start + book token) makes a tentative calendar hold on the configured booking backend (calrs at cal.scull7.com). The backend event type owns the meeting length; the stored hold row defaults to 1 hour for cap math. Which backend, host, and event type are used is configurable.
- [x] Sessions, tokens, and holds persist in Turso.
- [x] Free-email domains (gmail, yahoo, hotmail, outlook.com, icloud) are rejected unless allowlisted. The blocklist is configurable. Creating a hold emails Nathan a notification that includes one-click **ban this address** and **ban this domain** links.
- [x] A work domain cannot have more than N active tentative holds at once (default N=3). The cap is configurable.
- [x] `create_hold` is refused until the session has completed the required question set. A refusal does not count as completing an item. Default set is the five locked items; the set is configurable.
- [x] `/openapi.json` and `/mcp` are real (not stubs). MCP tools are exactly the five named in the spec.
- [x] Optional `callback_url` can receive `interview.completed` and `booking.requested`.
- [x] `/llms.txt` when-to-use describes this product. No street address is published. Contact remains `nathan@vegasbuckeye.com` / https://scull7.com.
